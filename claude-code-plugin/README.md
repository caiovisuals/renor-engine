# Renor's Claude Code plugin

Renor's Claude Code plugin is published from its own repository (github.com/renorai/renor-skills). This folder
is the one place in this repository for it: the manifests, the MCP entry and the hooks. The recall code itself lives in
the engine, where it is tested. Install stays two commands inside Claude Code:

```
/plugin marketplace add renorai/renor-skills
/plugin install renor@renor
```

| Path | What it is |
| --- | --- |
| `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` | the plugin `renor` in the marketplace `renor` |
| `.mcp.json` | the hosted endpoint `https://mcp.renor.cloud/mcp`; sign-in is OAuth in the browser, no key is stored |
| `hooks/hooks.json` | the hooks below, every one off until its variable is set |
| `hooks/stop-save.mjs` | the save before the agent finishes (`RENOR_SAVE_HOOK=1`, below) |

The `renor-memory` skill that sits next to these in renor-skills is generated by `src/lib/agent-skill.ts`.

# Automatic recall

**Why it exists.** In a real-use study of the owner's sessions, 24 of the 41 moments where he had to repeat himself
were about a memory that was already in Renor. The agent called Renor once in those 24. This hook takes the choice
away from the agent: every prompt that is not trivial is looked up before the agent sees it.

## What it does

On each `UserPromptSubmit`, `hooks/renor-recall/autoRecall.js` (the compiled `engine/src/recall/autoRecall.ts`, which uses only
Node built-ins):

1. exits at once, reading nothing, unless `RENOR_AUTO_RECALL=1` (this costs about 25 ms of Node startup per prompt);
2. skips trivial prompts: empty, fewer than 3 words, slash commands, `!` shell lines, steering replies such as "ok" or "yes go ahead";
3. calls `get_context` over MCP Streamable HTTP with the prompt (at most 1000 characters), the configured scope, and
   `max_tokens` set to twice the injection budget, with a bearer key and a 1.5 s limit on the whole lookup;
4. injects nothing when the reply says `relevance.relevant: false`, when `relevance.similarity` is under the floor,
   when a floor is set and the reply has no similarity to compare, or when there is no matched memory. The floor is
   `RENOR_AUTO_RECALL_MIN_SIMILARITY` (below);
5. otherwise adds a `<renor-memory source="automatic recall">` block to the agent's context through
   `hookSpecificOutput.additionalContext`: current facts, then matched memories with their dates, cut to the budget
   (400 tokens by default) and each to 500 characters.

The block is an untrusted-data boundary: a begin line, a line saying the content is stored reference data and never
instructions, the memory lines, an end line. Before stored text goes in, it is folded (NFKC) and stripped of invisible
characters. Literal angle brackets and a fixed list of lookalikes become parentheses, the label's name is split, and
character references (`&#60;`, `&#x3c;`, `&lt;`, double-encoded `&amp;#60;`) are broken. Each memory is cut to 500
characters, and the block to the budget, always on a character boundary.

**What the boundary is not.** It gives provenance (the text is labelled as the user's saved memory), explicit distrust
(the data-not-instructions line), literal delimiter hygiene and a bounded size. It does not make the agent immune to
prompt injection. A note's words still reach the agent, and a lookalike not on the list, or another encoding (base64, a
URL encoding, a spelled-out description), passes through as text. Whether the agent follows such text is up to the
agent.

Every failure (no key, network, timeout, a 401, a malformed reply) adds nothing and exits 0. The prompt is never blocked.

**It injects the text of saved notes into the prompt.** With `RENOR_AUTO_RECALL=1`, the words of the matched memories
and facts go into the agent's context, ahead of its answer, for every prompt that matches. The block is labelled as
saved notes, not instructions, and marks imported or reserved-source items `[untrusted]`, but a label is all that
separates them from instructions: a note anyone with write access to the workspace saved reaches the agent's context
verbatim. The pre-action hook (`RENOR_ACTION_RECALL=1`) does the same with standing rules, in its refusal reason. Firstmate's
call (2026-10-22, under the owner's standing product authority) is to keep injecting the text, inside an explicit untrusted-data boundary; that hardening is
its own change to `src/recall/autoRecall.ts`.

**Receipt (`RENOR_RECALL_RECEIPT=1`, off by default).** When step 5 injected something, the hook also returns one line
for the user in `systemMessage`, which Claude Code shows in the chat (the memories stay in `additionalContext`, which only
the model reads): `Renor recalled 3: 2 notes (Oct 18, Oct 19), 1 fact`. It holds counts and dates only, never a word of a
memory or a fact, because whatever the user saved would otherwise be on screen and in stream-json logs. No injection, no
line (`src/recall/receipt.ts`).

Settings are environment variables, which Claude Code passes to hooks from the `env` block of `~/.claude/settings.json`.
They are listed in [docs/ENVIRONMENT-VARIABLES.md](../docs/ENVIRONMENT-VARIABLES.md#automatic-recall-claude-code-hook).

```json
{ "env": { "RENOR_AUTO_RECALL": "1", "RENOR_AUTO_RECALL_TOKEN": "<a Renor API key>" } }
```

**Keep it off unless you are measuring it.** It is off by default because a check on the owner's own private sessions
did not show a clear gain and showed noise on unrelated turns. That check is private and not reproducible from this
repository. Leave `RENOR_AUTO_RECALL_SCOPE` unset unless your saved scopes are named after your folders.

**The relevance floor.** With no `RENOR_AUTO_RECALL_MIN_SIMILARITY` set:
- the hosted endpoint (`https://mcp.renor.cloud/mcp`) gets a floor of 0.68;
- any other endpoint gets none.

0.68 is a cosine for the hosted model's embeddings only (`vertex:gemini-embedding-001:768`, the one model with a
calibrated bar in `src/mvp/contextRelevance.ts`). It was chosen on the same private sessions, so it is in-sample and not
reproducible here. A bar never carries over to another model.

A floor needs a number to compare, so a reply without `relevance.similarity` is dropped while a floor applies. The
server gives none when relevance judging is off, when there is no query vector, when its model has no calibrated bar
(any self-hosted provider today: `none`, `local`, `openai`), and while fact vectors are still warming. The hook says so
once per endpoint on stderr. Set the variable to:
- a number between -1 and 1 for another floor;
- `none` (or `off`, `false`, `no`) for no floor, which is what a self-hosted engine needs.

Anything else is ignored with a line on stderr, and then no floor applies.

## Pre-action recall (`RENOR_ACTION_RECALL=1`, off by default)

The same file also runs on `PreToolUse` (matcher `Bash|AskUserQuestion|mcp__.*`). It classifies the call locally, and
anything that is not one of these exits at once:

- merging: `gh pr merge`, `glab mr merge`, `git merge`, `git push` to main or master, an MCP tool named `*merge*`;
- releasing: `gh release create`, `npm`/`pnpm`/`yarn`/`cargo publish`, `twine upload`, pushing tags, a version tag, an MCP `*release*`/`*publish*`;
- deploying: `vercel`/`netlify ... deploy`, `wrangler deploy`, `fly deploy`, `kubectl apply|rollout`, `helm upgrade|install`,
  `terraform apply`, `supabase db push|functions deploy`, `firebase deploy`, `gcloud ... deploy`, `docker push`, `npm run deploy|release`,
  `deploy*.sh`, an MCP `*deploy*`;
- spending money: `stripe ... create`, cloud instance creation (`aws ec2 run-instances`, `gcloud compute instances create`,
  `az vm create`, `doctl ... create`), `curl` to a paid model API, an MCP tool with a payment word part (`create_payment`, `checkout`);
- asking the user: `AskUserQuestion`.

For a gated call it asks `get_context` for that action's standing rule, plus what is about to run. It drops versions a
later correction replaced (`replaced`) and unmatched filler, and keeps the best three by the reply's own ranking
(current facts first). It shows them newest first with their dates, in a `<renor-rules action="...">` block of at most
250 tokens.

**When the agent sees them.** Claude Code adds a `PreToolUse` hook's `additionalContext` "alongside the tool result"
(code.claude.com/docs/en/hooks), which is after a merge has happened. Only a denial's `permissionDecisionReason` reaches
Claude before the tool runs. So the default mode, `gate`, refuses the first such action of each kind per session
(once in 30 minutes) with the rules as the reason. The block says to run the same call again to go ahead, and the retry
passes. `RENOR_ACTION_RECALL_MODE=context` never refuses and adds the rules next to the result instead. If the gate
cannot record that it fired (an unwritable temp directory), it uses `context`, so it never refuses twice. A failure, a
timeout, or no relevant rule lets the tool run without a word.

**What hides a superseded rule, and what does not.** Facts are current by default, and a memory saved with
`replaces` is marked and dropped. A new rule saved as a plain statement after an old one is not linked to it. Both can
show, newest first with dates. On the offline eval (`scripts/eval/agent-workflow/pre-action.ts`), the linked old rule
never showed, and the plain one always did.

| Client | Event that sees the action before it runs | Can it put text in front of the agent first? |
|---|---|---|
| Claude Code | `PreToolUse` on `Bash`, `AskUserQuestion`, `mcp__<server>__<tool>` (MCP), and others | Only through `deny` + `permissionDecisionReason` (the gate). `additionalContext` arrives with the result. |
| Codex | `PreToolUse` on `Bash`, `apply_patch` and MCP tools (developers.openai.com/codex/hooks) | `deny` + `permissionDecisionReason` (the same JSON as Claude Code), or `additionalContext`. The docs do not say whether that arrives before or after the call. `ask` is not supported yet. |
| Cursor | `preToolUse` (every tool) and `beforeShellExecution` / `beforeMCPExecution` (cursor.com/docs/hooks) | `permission: "deny"` + `agent_message`. Run the hook with `--cursor`: Cursor blocks on invalid JSON, so that mode always prints a valid `{"permission":"allow"}`. The gate keys on `conversation_id`, which every Cursor hook input carries. |

None of these three was run live with this hook. The JSON shapes come from each client's documentation, as read on
2026-10-21.

## Standing rules at session start (`RENOR_STANDING_RULES_HOOK=1`, off by default)

`hooks/standing-rules/session-start.mjs` runs on `SessionStart` (matchers `startup`, `clear`, `compact`; a resume or fork
keeps the transcript). It puts the standing rules **the owner approved** in front of the agent, with no query, newest
first and dated, each with the agent that saved it, in at most 300 tokens (`RENOR_STANDING_RULES_MAX_TOKENS`):

```
<renor-standing-rules>
Standing rules the user approved in Renor, newest first by date saved, each with the agent that saved it. Follow them unless the user says otherwise now.
2026-10-22:
- merge rule: never push to main; open a PR, firstmate merges (saved by Claude-Code)
(1 saved rule not shown: the user has not approved it.)
A new lasting rule from the user: save it with remember, subject "standing rule"; it is shown once the user approves it.
</renor-standing-rules>
```

**Marked, then approved.**
- A standing rule is a fact saved with `remember` under the reserved subject `standing rule` (predicate a short topic,
  object the rule), by the agent when the user states a lasting rule, or on an existing memory (with `cites`). The hook
  reads them with `retrieve_memory`: no engine change.
- Anyone who may save a fact can save one, so saving is not authority. A rule becomes an instruction only when the owner
  approved its exact saved event (id, scope, topic, text, author) from a terminal:
  `RENOR_CONNECT_TOKEN=<key> node hooks/standing-rules/approve.mjs` (and `--list` to see each rule's state). The
  approvals file (`RENOR_STANDING_RULES_APPROVALS`, default `~/.renor/standing-rules-approved.json`, mode 0600) stays on
  the owner's machine. A rule that changes is a new event and needs approving again. An unapproved rule is only counted,
  never shown; an import (untrusted) is never listed. `approve.mjs` needs an interactive terminal, which an agent's shell
  tool does not have. Something that can write the owner's files can also write the approvals file, as it can write
  CLAUDE.md: that is outside what this guards against.

**Privacy.** Every value is screened before it is shown, whatever `RENOR_PRIVACY_MARKERS` says: a `<private>` region
becomes `[private]`, and a topic or text starting with `#norecall` drops the rule (`hooks/standing-rules/privacy.mjs`,
the rule of PR 861, checked against its vectors). A rule's scope and author are stored normalized, with markup cut out
and the words kept, so a marker there cannot be undone: a rule whose scope or author holds the letters `private` or
`norecall` is never shown (nor offered by `approve.mjs`), including a project merely named that way.

**The token.** A `command` hook cannot use the sign-in Claude Code holds, so it uses a connect token:
`RENOR_CONNECT_TOKEN`, else `RENOR_AUTO_RECALL_TOKEN`. It is sent only to an `https` endpoint (`RENOR_MCP_URL`, default
`https://mcp.renor.cloud/mcp`) or over `http` to `127.0.0.1` / `[::1]` (not the name `localhost`), and a redirect is
refused. Every failure prints nothing and exits 0; `RENOR_HOOK_DEBUG=1` names the kind of failure (`invalid-endpoint`,
`timeout`, `network`, `http-401`, `tool-error`, ...), never text the server sent or the token.

```json
{ "env": { "RENOR_STANDING_RULES_HOOK": "1", "RENOR_CONNECT_TOKEN": "<a Renor connect token>" } }
```

**The private gate (owner's laptop)**, read-only:
`RENOR_CONNECT_TOKEN=<key> node hooks/standing-rules/standing-rules-gate.mjs --cases <cases.jsonl> --mark <facts.jsonl> --print`.
Cases are `{"id", "kind": "rule", "expect": [...], "moments": n}`; each mark line names an existing fact
(`{"subject", "predicate"}`) to show as if marked and approved. Nothing is written.

To put it in one script with another SessionStart hook, import `standingRulesBlock(client, { approvals, maxTokens })`
from `hooks/standing-rules/standing-rules.mjs`; the block is wrapped in `<renor-standing-rules>`.

## Save before the agent finishes (`RENOR_SAVE_HOOK=1`, off by default)

On `Stop`, `hooks/stop-save.mjs` looks for what the user explicitly said to keep this session and Renor does not hold
yet: their own sentences that open with "remember that", "please remember", "from now on" or "going forward". If there
is any, it stops the agent once (`decision: block`) and lists the dated statements for it to save with its own
`remember` tool. The hook holds no key and opens no connection, so every save is screened by the server as any other
(`RENOR_SECRET_GUARD`, and the Jev save screen for an opted-in workspace).

What it never offers: a bare "yes" to an agent's proposal (mostly an action such as "commit and push this"), anything a
classifier would have to guess, assistant text, tool calls and output, subagent and meta lines, slash commands, system
reminders, code blocks, and anything inside `<private>...</private>`. It is silent when there is nothing new or
`stop_hook_active` is set, offers a line once per session (state in `RENOR_HOOK_STATE_DIR`, else `$CLAUDE_PLUGIN_DATA`,
else `~/.renor/hooks`) and once more if the agent's save of it failed, skips a line `remember`, `save_memory` or
`remember_note` saved in the transcript (matched to its `tool_result` by id; a result with `is_error`, or none, is not a
save), and offers at most 5 per stop. Widening it to decisions and preferences the user did not flag waits for a decision gate
that passes the owner's labelled set.

## Shipping it in renor-skills (not done by this change)

This folder is the source, not the publishable plugin: the recall hooks and the secret scanner are compiled engine
modules. Build the plugin with one command (from `engine/`):

```bash
node scripts/plugin/pack-claude-code-plugin.mjs <out-dir>
```

It compiles the engine, writes `<out-dir>` (missing, empty, or packed before; anything else is refused), copies
`hooks/standing-rules/` and `hooks/stop-save.mjs`, adds `hooks/renor-recall/` (`autoRecall.js`, `actionRecall.js`) and
`hooks/lib/secretScanner.js` from `dist/`, and checks
the result: every command in `hooks/hooks.json` names a file in `<out-dir>`, and each runs with no settings, exits 0 and
prints nothing. Copy `<out-dir>` into the root of renor-skills, next to `skills/renor-memory`. Every hook is off until a
user sets its variable. `tests/claude-plugin/plugin.test.ts` packs it the same way on every run.

## What each hook sends and stores

| Hook | Sends | Stores | Key |
| --- | --- | --- | --- |
| recall (`RENOR_AUTO_RECALL=1`, `RENOR_ACTION_RECALL=1`) | the prompt, or the gated action, to `get_context` | a per-session gate mark in the temp directory (pre-action only) | `RENOR_AUTO_RECALL_TOKEN`, read from the environment (the `env` block of `~/.claude/settings.json`), sent only as the bearer, only to `https://` or to `http://127.0.0.1` / `http://[::1]`, and never across a redirect |
| save (`RENOR_SAVE_HOOK=1`) | nothing: it opens no connection; the agent saves with its own OAuth `remember` | the lines it offered, in `stop-<session>.json` (0600) under `RENOR_HOOK_STATE_DIR`, `$CLAUDE_PLUGIN_DATA` or `~/.renor/hooks` | none |

No key is in `plugin.json`, `.mcp.json` or any other plugin file, and no hook writes one to a file. A line the secret
scanner flags is never offered for saving, and the server refuses a secret in any save (`RENOR_SECRET_GUARD`, on by
default) before writing anything.

1. `cd engine && npm run build`, then copy `dist/recall/` (`autoRecall.js`, `actionRecall.js` and `receipt.js`) into the plugin as
   `hooks/renor-recall/`.
2. Copy `hooks/hooks.json` from this folder into the plugin. It is off until a user sets `RENOR_AUTO_RECALL=1`.

## What is not verified

- **The hosted path with a real key.** The gateway accepts a dashboard connect token as a bearer
  (`apps/gateway/src/oauth.ts`, header comment). The full exchange (initialize, initialized, tools/call, SSE) is tested
  against a local fake server (`tests/recall/auto-recall.test.ts`). Against `mcp.renor.cloud` only the refusal was
  tested: a bogus key gets a 401, and the hook adds nothing. No real key was available, so a successful hosted lookup
  and its latency are not measured.
- **Behind an HTTP proxy.** Node's `fetch` ignores `HTTPS_PROXY` unless `NODE_USE_ENV_PROXY=1` is set (Node 22.21 and
  later). Verified in a proxied sandbox on 2026-10-21: without it, the lookup failed on DNS (`ENOTFOUND`) and added
  nothing. With it, the hook reached `mcp.renor.cloud`, got a 401 for a bogus key and exited 0 in about 0.66 s. A user
  behind a corporate proxy needs that variable in the `env` block, or the hook silently does nothing.
- **The plugin key.** The plugin's own MCP connection signs in with OAuth, and a hook cannot read that token. So a
  user who turns the hook on also creates an API key. Each lookup then shows in the dashboard as that key's connection.
- **Self-hosted.** The stdio server (`dist/cli.js mcp`) has no `get_context`, and the HTTP server (`npm run mvp`) accepts
  only short-lived OAuth tokens (`src/mvp/auth.ts` `verifyAccessToken`), so the hook does not serve self-hosted users yet.
- **Plugin hooks firing.** anthropics/claude-code#10225 reported that plugin `UserPromptSubmit` hooks did not run in
  2.0.24, while the same hook in `~/.claude/settings.json` did. Check this on the current Claude Code before relying on it.

## Codex and Cursor (per-prompt recall)

Per the clients' documentation, read on 2026-10-21. Neither client was run live with this hook.

- **Codex**: `UserPromptSubmit` takes the same output, `hookSpecificOutput.additionalContext`, "added as extra developer
  context", and its stdin carries `prompt` (developers.openai.com/codex/hooks). The same file should work from
  `~/.codex/hooks.json`. Codex asks the user to review and trust a non-managed command hook before it runs.
- **Cursor**: `beforeSubmitPrompt` returns only `continue` and `user_message` (cursor.com/docs/hooks), so it cannot add
  context to a prompt. `sessionStart`'s `additional_context` runs once per conversation. Per-prompt recall is not
  possible in Cursor today. Pre-action recall is possible there (above).

## Replay

`recallRequest(prompt, config)` returns what the hook would send, or why it skips. `presentRecall(reply, config)`
returns what it would inject. `autoRecall(prompt, config, caller)` runs both around any `get_context` caller. A replay of
real sessions can call them on recorded prompts with its own caller.
`scripts/eval/agent-workflow/auto-recall.ts` is the offline example.
