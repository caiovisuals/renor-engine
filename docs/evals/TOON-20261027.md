# Fixed opt-in TOON evaluation — 2026-10-27

`RENOR_MCP_RESPONSE=toon` changes successful HTTP `search_memory` text replies to
TOON, prefixed with `Format: TOON\n`. JSON remains the default. The profile does
not count tokens or choose a format per reply. Empty successes also use TOON.
`get_context`, `search_text`, other tools, the directory/stdio client and Markdown
storage keep their existing behavior. Existing refusals stay JSON.

This is an evaluation profile, not a recommendation to change the default. The
public fixtures favor it in aggregate; the prose controls below also demonstrate
regressions. Model comprehension and retrieval accuracy with TOON remain unverified.

## Contract and safety

The encoder receives the existing JSON reply value after retrieval and trimming.
Fields, hit order, provenance, trust markers and correction metadata are retained.
`structuredContent`, when enabled, remains the original object; the profile only
replaces `content[0].text` on successful searches.

Hidden BMP characters remain visibly escaped, including bidi and zero-width
controls. Ordinary Unicode and emoji round-trip. TOON does not accept escaped
surrogate pairs or lone surrogates. If a reply cannot be represented without
exposing hidden supplementary characters, invalid scalars or unsafe keys, the
profile returns an explicit JSON `isError` refusal with
`error: "toon-encoding-unsupported"` and no `structuredContent`. It does not
silently drop characters or return a successful JSON fallback. The default JSON
profile remains available for such data. This additional refusal is a compatibility
limitation of the experimental profile.

## Method

Measured on 2026-10-27 with Node v22.23.4, darwin/arm64, `@toon-format/toon` pinned
to 4.4.0, and the repository's o200k token counter checked against `gpt-tokenizer`
for every successful comparison. The branch starts at
`8a738cae90c57ab47e6942252a003fe4cfcaed9d`. Runs used a working tree with the changes
in this PR and `--allow-dirty`; they are explicitly non-promotable evaluation runs.
No paid or downloaded embedding model was used: all product runs used `eval-hash`.

The product runner calls the real MCP server through the SDK's in-memory transport.
JSON and TOON runs use the same fixtures, calls and arguments. The comparison
checks the entire served TOON result against the expected conversion, decodes it
back to the JSON value, and checks `get_context` results remain identical. Capture
continues across the v1 erasure/rebuild restart. Missing search captures fail the
evaluation instead of producing an empty success report.

Two token views are measured: the final text including the format header, and
`JSON.stringify` of the whole MCP result. The second is a transport representation,
**not** measured client/model usage or billing. Synthetic variants with and without
`structuredContent` show how duplicate structured data changes the total.

All 398 paired search results matched the expected representation; one grew.

Hypothetically converting those context replies would exceed `max_tokens` in 22
cases. This is why this profile leaves budgeted context replies as JSON.

## Prose-heavy and multi-line controls

The synthetic corpus uses 1, 6 and 24 hits, each with long prose, either in one
paragraph or with paragraph breaks, fenced code, quotes, commas, tabs and Unicode.
Uniform records share fields; mixed records vary optional fields and include
nested correction metadata. These are plausible reply shapes, not measured
production frequencies or a reproduction of any private corpus.

Each row below aggregates the three hit counts. Text tokens are identical in the
variants with and without `structuredContent`.

Additional controls include short uniform records (633 → 453 text tokens), an
empty result (8 → 12), and BMP controls (47 → 58). They confirm both savings and
growth are exercised. Four synthetic variants are unsupported (supplementary
invisible characters and lone surrogates, each with/without structured content).
They are reported separately, excluded from successful token totals, and must not
be interpreted as zero-cost responses. The corpus contains 34 synthetic variants
in total. Real MCP tests also exercise multiline text, hidden controls and the
explicit unsupported-character refusal.

## Performance model and limits

The target cost is tokens carried in retrieved tool text. It grows with both the
number of hits and their text/metadata size. Repeated keys in uniform records can
be represented once; long prose leaves a smaller fraction of removable syntax,
and heterogeneous/nested records can need more syntax. The measured cost is
`tokens(final_text)` on identical reply values, including the TOON header.

This changes representation overhead, not the asymptotic retrieval algorithm.
Both formats remain linear in the amount of represented data under a fixed
schema. There is no universal non-regression guarantee and no Big-O improvement.
TOON also adds parsing and encoding work after the existing JSON serialization.
The report records warm serialization wall times and materialized string bytes;
these are diagnostics, not end-to-end latency, CPU profiles or peak heap/RSS.
No production traffic mix, client billing or model accuracy was measured.

The runner decodes TOON before scoring the retrieved content. Equal content scores
therefore verify representation fidelity, not an LLM's ability to use TOON. The
maintainer's retrieval/agent benchmarks remain the gate for any use beyond opt-in.
The evaluator source hash changes with capture support; committed comparison
baselines are intentionally not regenerated by this PR.

## Reproduce

Use the repository's tested Node 22 environment and `npm ci`. From a clean checkout
of this PR, run the public product suites twice:

```sh
for suite in v1 v2 documents; do
  node --import tsx scripts/eval/run-renorbench-product.ts \
    --suite "$suite" --provider hash --capture-replies \
    --output ".eval-runs/toon/$suite-json"
  node --import tsx scripts/eval/run-renorbench-product.ts \
    --suite "$suite" --provider hash --capture-replies \
    --env RENOR_MCP_RESPONSE=toon \
    --output ".eval-runs/toon/$suite-toon"
done

node --import tsx scripts/eval/eval-toon.ts \
  --capture .eval-runs/toon/v1-json/replies.jsonl \
  --capture .eval-runs/toon/v2-json/replies.jsonl \
  --capture .eval-runs/toon/documents-json/replies.jsonl \
  --toon-capture .eval-runs/toon/v1-toon/replies.jsonl \
  --toon-capture .eval-runs/toon/v2-toon/replies.jsonl \
  --toon-capture .eval-runs/toon/documents-toon/replies.jsonl \
  --output .eval-runs/toon/report.json
```

For synthetic controls alone, omit all capture arguments. Output must be a new
file. Working-tree experiments require `--allow-dirty` on the product runs and
are marked non-promotable. Capture artifacts contain synthetic fixture content;
do not publish captures from private vaults.

The JSON report contains per-case metrics, decoded-body digests, input capture
digests, implementation/lockfile/encoder digests, and aggregate comparisons.
Product manifests also bind captures, fixtures and cases to their hashes.
The renderer measured here has SHA-256
`4db93a98a6d6829cc8ebe948ca0234c62702ac7dc8e6778a4ab8fbd1ecfca4c6`;
the installed encoder entry point has SHA-256
`3795bdfd3c1f2e71d76920540ab02a0b15436efc5a56b8346d701a7e343ccbd5`.
